# 03 – Cílová architektura webové aplikace

## 1. Shrnutí rozhodnutí

| Oblast | Volba |
|---|---|
| Backend | **Python 3.12 + Django 5.x** (server-rendered) |
| Frontend | **Django templates + HTMX** pro dílčí interakce, **Pico.css** (classless CSS, vendorováno do `static/`), žádný build krok |
| Databáze | **PostgreSQL 16** |
| ORM / migrace | Django ORM + Django migrations |
| Autentizace | Django auth, vlastní model uživatele (`username = EMPID`), role odvozená z oddělení |
| Testy | `pytest` + `pytest-django` + `factory-boy`; e2e **Playwright (Python)** |
| Kvalita kódu | `ruff` (lint + format), `django check`, `makemigrations --check` |
| Běh | **Docker Compose** (`db`, `web`), `Makefile` s jednotnými příkazy |
| Umístění | vše v `app/`; legacy adresáře zůstávají netknuté |

## 2. Porovnání variant stacku

Kritéria jsou vážena podle situace: PoC přepisu, implementace po malých PR agentem (Codex), obrazovky jsou formulářové (CICS mapy), tým bez dedikovaného frontendisty, nutnost lokálního spuštění včetně e2e testů bez CI.

| Kritérium | A) Django + templates + HTMX | B) Django + DRF + React/Vite SPA | C) FastAPI + SQLAlchemy/Alembic + React/Vite SPA |
|---|---|---|---|
| Počet technologií / repozitářů | 1 jazyk, 1 proces, 0 build kroků | 2 jazyky, 2 build pipeline, CORS/CSRF, API kontrakt | 2 jazyky + ručně psaná auth, sessions, admin, migrace |
| Vhodnost pro formulářové obrazovky 1:1 z CICS map | Výborná – formulář = view + template, validace na serveru (jako v COBOLu) | Dobrá, ale každá obrazovka = endpoint + komponenta + typy | dtto B |
| Auth, role, admin, migrace, formuláře „z krabice“ | Ano | Ano (backend), frontend řeší sám | Ne (nutno psát nebo skládat z knihoven) |
| Velikost jednoho kroku pro Codex | Malá – jeden PR = jedna obrazovka včetně testů | Střední – PR musí měnit API i UI, nebo se rozpadá na 2 PR | Větší |
| Testovatelnost bez CI | Django test client pokryje 90 % bez prohlížeče; e2e jen pro klíčový tok | Nutné e2e/prohlížečové testy pro každou obrazovku | dtto B |
| Výkon / škálování | Dostatečné pro interní systém desítek uživatelů | Lepší UX při vysoké interaktivitě (nepotřebujeme) | Nejrychlejší API (nepotřebujeme) |
| Riziko pro PoC | Nízké | Střední (koordinace API/UI) | Vyšší (více vlastního kódu) |

**Volba: A.** Varianta B je rozumný krok „poté“, pokud se z PoC stane produkt s náročným UI; DRF lze přidat nad stejné modely bez přepisu. Varianta C dává smysl pro čistě API službu, což tento systém není.

HTMX se používá pouze tam, kde legacy měl dílčí interakci v rámci obrazovky (dohledání jména cestujícího po zadání `CLIENTID` v kroku 2 prodeje, stránkování). Vše musí fungovat i bez JavaScriptu (plný POST/GET), HTMX jen zlepšuje odezvu.

├── fleet/                      # Airport (AIRPORT), Airplane (AIRPLANE) + IT číselníky
├── operations/                 # Crew (CREW), Shift (SHIFT), Flight (FLIGHT) + Schedule obrazovky, generování letů
├── sales/                      # Passenger (PASSENGERS), Buy (BUY), Ticket (TICKET) + Sales obrazovky, prodej, tisky

Business logika (prodej, přidělení sedadla, výpočet volných míst, generování letů) žije v modulech `services.py` jednotlivých aplikací, ne ve views. Views jsou tenké (formulář → služba → šablona).

## 4. Mapování DB2 → PostgreSQL

### 4.1 Typy

| DB2 | PostgreSQL | Django field |
|---|---|---|
| `CHAR(n)` (identifikátory `EMPID`, `AIRPLANEID`, `TICKETID`, `FLIGHTNUM`, `SEAT`) | `varchar(n)` (bez doplňování mezerami) | `CharField(max_length=n)` |
| `VARCHAR(n)` | `varchar(n)` | `CharField(max_length=n)` |
| `INT` | `integer` | `IntegerField` |
| `INT GENERATED BY DEFAULT AS IDENTITY` | `integer GENERATED BY DEFAULT AS IDENTITY` | `AutoField` (PK) |
| `DATE` | `date` | `DateField` |
| `TIME` | `time` | `TimeField` |
| `DEC(8,2)`, `DEC(7,2)` | `numeric(8,2)`, `numeric(7,2)` | `DecimalField(max_digits, decimal_places=2)` |
| `NOT NULL` | `NOT NULL` | `null=False` (výchozí) |
| `FOREIGN KEY … ON DELETE RESTRICT` | `REFERENCES … ON DELETE RESTRICT` | `ForeignKey(on_delete=PROTECT)` |
| unikátní indexy nad PK | implicitní PK index | – |

### 4.2 Tabulky a názvy

Zásada: **názvy tabulek a sloupců zůstávají legacy, malými písmeny** (`db_table`, `db_column` = původní název). Modely mají pole pojmenovaná stejně (`flightnum`, `airportdep`), aby byla dokumentace, DDL a kód vzájemně dohledatelné. Výjimka: cizí klíče se v modelu jmenují bez přípony `id` (`dept`, `airplane`, `client`, `flight`, `buy`, `emp`, `shift`, `crew`; `airportdep`/`airportarr` zůstávají), sloupec je legacy (`db_column="deptid"`), takže Django nabízí `flight.airplane` i `flight.airplane_id`. Vztahy mají `related_name`. Detailní definice polí: `codex-tasks/R02.md`.

| DB2 tabulka | PostgreSQL tabulka | Django model (app) | Změny oproti DDL |
|---|---|---|---|
| `AIRPORT` | `airport` | `fleet.Airport` | `airportid varchar(4)` PK; `country NOT NULL` |
| `AIRPLANE` | `airplane` | `fleet.Airplane` | beze změn; `CHECK numseats > 0` |
| `DEPT` | `dept` | `accounts.Department` | `deptid` je ruční PK (1–9, `IntegerField(primary_key=True)`); `manager` nullable FK, **deferrable** kvůli cyklu s `emplo` |
| `EMPLO` | `emplo` | `accounts.Employee` | `empid varchar(8)` PK; `telephone varchar(20)`; nový `user_id` 1:1 na `accounts_user` (nullable) |
| `CREW` | `crew` | `operations.Crew` | 6 FK na `emplo`; `CHECK` všech 6 různých (na úrovni aplikace) |
| `SHIFT` | `shift` | `operations.Shift` | `CHECK begintime < endtime` |
| `FLIGHT` | `flight` | `operations.Flight` | nový `price numeric(7,2) NOT NULL DEFAULT 120.99`; `UNIQUE (flightnum, flightdate)`; index `(flightdate, deptime)`; `airportdep/arr varchar(4)`; `CHECK airportdep <> airportarr` |
| `PASSENGERS` | `passengers` | `sales.Passenger` | `country NOT NULL`; index `(upper(lastname), upper(firstname))` |
| `BUY` | `buy` | `sales.Buy` | beze změn; index `(buydate)` |
| `TICKET` | `ticket` | `sales.Ticket` | sloupec `seat` (dle DDL); `UNIQUE (flightid, seat)`; `UNIQUE (flightid, clientid)`; sekvence `ticket_ticketid_seq` pro generování `CB########`; indexy `(clientid)`, `(flightid)` |
| – | `accounts_user` | `accounts.User` (AbstractUser) | nová: `username` = `EMPID`, `password` (hash), `is_active`, `last_login`, `must_change_password bool` |

Cyklus `emplo.deptid → dept` a `dept.manager → emplo`: v PostgreSQL se `dept.manager` definuje jako `DEFERRABLE INITIALLY DEFERRED`; Django to řeší tím, že `manager` je nullable a plní se ve druhém kroku (stejně jako legacy `insertion-2`).

### 4.3 Klíče a integrity navíc oproti legacy

- `flight (flightnum, flightdate)` unikátní – legacy implicitně předpokládá (`SELLCOB1`).
- `ticket (flightid, seat)` a `ticket (flightid, clientid)` unikátní – pravidla kap. 5 spec.
- `passengers.email` **není** unikátní (legacy data mohou mít duplicity).
- `emplo.email` není unikátní (v testovacích datech se opakují telefony i adresy).

## 5. Mapování CICS obrazovek → web

Detailně v `02-functional-spec.md` kap. 4. Technický vzor:

| CICS koncept | Web ekvivalent |
|---|---|
| Transakce + program + mapa (`SCHF` / `SRCHFLY` / `SRCHPA`) | URL + view + šablona (`/sales/flights/` → `sales.views.flight_search` → `sales/flight_search.html`) |
| `RECEIVE MAP` / `SEND MAP` | HTTP GET (vyhledávání) nebo POST (zápis) → render šablony |
| `COMMAREA` mezi transakcemi | Session (`request.session['sale']`) pro vícekrokový prodej; jinak query parametry |
| `EIBAID` (F-klávesy) | Odkazy v menu / tlačítka formuláře (`name="action"`) |
| Symbolická mapa (`xxxI`/`xxxO`) | Django `Form` (vstup) + context šablony (výstup) |
| `MSG1`/`MSG2` | Django messages framework (`error`, `info`, `success`) |
| `XCTL LOGIN` (F3) | `/logout/` |
| `SPOOLOPEN INTRDR` + JCL `PRINTCI` | Tisková HTML stránka + `window.print()`; volitelně WeasyPrint PDF |
| DB2 kurzor s limitem 10 | QuerySet + `Paginator(page_size=10)` |
| `SQLCODE 100` | `Model.DoesNotExist` → hláška |
| `SQLCODE < 0` | výjimka → 500 handler s E-SYS-01 |

## 6. Autentizace a autorizace

- Vlastní `accounts.User(AbstractUser)`; `username` = `EMPID` (8 číslic). `Employee.user` je `OneToOneField(User, null=True)`. Uživatel bez `Employee` je jen superuser pro `/admin/` (vývoj).
- Přihlášení: standardní Django `LoginView` s vlastní šablonou (`LOGON`), stejná hláška pro neexistujícího uživatele i špatné heslo. `django-axes` nebo jednoduchý cache-based limiter pro 10 pokusů / 15 min (krok R18).
- Hashování: `PASSWORD_HASHERS` = Argon2 (balíček `argon2-cffi`) s PBKDF2 fallbackem.
- **Role** se odvozuje za běhu: `Employee.role` = `ROLE_BY_DEPT[deptid]` (`{1: 'ceo', 2: 'crew', 3: 'crew', 4: 'crew', 5: 'hr', 6: 'it', 7: 'sales', 8: 'legal', 9: 'schedule'}`). Žádné synchronizované Groups – méně stavu.
- Dekorátor `@role_required('sales', 'ceo')` (a mixin pro CBV) vrací 403 se stránkou E-AUTH-02. Superuser má vše.
- Session: cookie, `SESSION_COOKIE_HTTPONLY`, expirace 8 h (pracovní směna), CSRF zapnuto.
- `must_change_password`: po resetu hesla IT podporou přesměrovává middleware na `/password/`.

## 7. Strategie migrace dat

### 7.1 Zdroje dat

1. **Testovací data v repozitáři** (k dispozici teď): `DB2/insertion-*` (číselníky, ručně přepsané do Python fixtures), `COB-PROG/EMPLO-INSERT/EMPLOYEE-LIST.json` (30 zaměstnanců + hesla), `COB-PROG/PASSENGER-INSERT/PASSENGER1..8.xml` (640 cestujících), vzory letů z `insertion-2/3` + logika `CBFLIGHT`.
2. **Export z produkční DB2** (k dispozici není, ale připravíme se): `EXPORT TO <TABLE>.csv OF DEL MODIFIED BY COLDEL, DATESISO TIMESTAMPFORMAT="HH:MM:SS" SELECT * FROM <TABLE>` pro každou z 10 tabulek, plus soubor `PASSDOC` (nepoužitelný – hesla se nemigrují).

### 7.2 Příkaz `seed_demo` (vývoj a e2e)

`python manage.py seed_demo [--flush] [--from-date YYYY-MM-DD --days N]`

- Načte číselníky (9 oddělení, 9 letišť, 10 letadel) z Python fixtures v `legacy_import/data/` (přepis `insertion-1..3` do ISO dat a s opravenými FK – viz inventář kap. 4.3).
- Zaměstnanci: parsuje `../COB-PROG/EMPLO-INSERT/EMPLOYEE-LIST.json` (cesta relativní ke kořeni repa, konfigurovatelná `LEGACY_ROOT`), `EMPID = 10000000 + empid`, datum `YYYY/MM/DD` → ISO, vytvoří `User` s heslem `passw` (jen v seedu!). Doplní 9 zaměstnanců z `insertion-3` (bez hesla → účet neaktivní).
- Manažeři oddělení dle `insertion-2`.
- Cestující: parsuje 8 XML souborů (UTF-8, element `PASSENGER-TABLE`), + Maxime Duprat; ukládá jména velkými písmeny (rekonstrukce `UPDATE1`).
- Posádky a směny: 4 posádky ze zaměstnanců správných oddělení (opravené neplatné `EMPID`), směny pro každý den letového období.
- Lety: 8 vzorů (`CB1104`…`CB4405`) pro **září 2022** (historická data, 240 letů) **a** pro okno `--from-date` (výchozí dnes) + `--days` (výchozí 60) – aby šlo v e2e prodávat. `price = 120.99`, `totpass = numseats`, `totbagga = 0`.
- Nákup + letenka `CB00000001` (Maxime Duprat, CB2204 2022-09-01, sedadlo B04, prodejce `10000006`) jako referenční záznam pro test tisku palubní vstupenky.
- Idempotentní: opakované spuštění nevytvoří duplicity (upsert podle PK / přirozeného klíče); `--flush` nejdřív smaže data aplikace.

### 7.3 Příkaz `import_legacy` (produkční export DB2)

`python manage.py import_legacy --dir <adresář s CSV> [--dry-run] [--report report.json] [--date-format iso|us]`

- Očekává soubory `AIRPORT.csv, AIRPLANE.csv, DEPT.csv, EMPLO.csv, PASSENGERS.csv, CREW.csv, SHIFT.csv, FLIGHT.csv, BUY.csv, TICKET.csv` (DEL formát DB2: čárka, text v uvozovkách, hlavička nepovinná – pořadí sloupců dle DDL).
- Pořadí importu respektuje FK: `airport, airplane, dept (bez manager), emplo, dept.manager, passengers, crew, shift, flight, buy, ticket`. Celý import v jedné transakci; `--dry-run` ji odrolluje.
- Normalizace: ořez mezer u `CHAR`, `airportid` velkými písmeny, datum přijímá ISO (`YYYY-MM-DD`, výchozí) nebo `MM/DD/YYYY` (americké lokální nastavení DB2 zjištěné v insert skriptech) – formát se volí explicitně přepínačem `--date-format iso|us` pro celý běh; hodnota mimo zvolený formát = chyba řádku (**odchylka** od původního návrhu autodetekce, viz `DECISIONS.md` 2026-09-12); `time` `HH:MM` i `HH:MM:SS`; `seat` doplněn na formát `X99`.
- `FLIGHT.price` neexistuje v exportu → výchozí 120.99. `EMPLO.telephone` delší než 20 → chyba řádku.
- Validace FK: řádek s neexistující referencí se přeskočí a zapíše do reportu (legacy data takové řádky obsahují).
- Sekvence `ticket_ticketid_seq` a identity se po importu nastaví na `max + 1`.
- Účty: pro každého `EMPLO` vznikne `User` neaktivní, bez hesla; IT provede reset (UC-I01). Report obsahuje seznam vytvořených účtů.
- Testy: fixture s ukázkovými CSV (po 3–5 řádcích, včetně chybných) v `tests/unit/legacy_import/`.

### 7.4 Co se nemigruje

- Hesla (`PASSDOC`) – neprolomitelně vázaná na IBM COBOL `FUNCTION RANDOM` a EBCDIC.
- JCL, tiskové spooly.
- AS/400 data (duplikují z/OS data).

## 8. Testovací strategie

### 8.1 Úrovně

| Úroveň | Nástroj | Co pokrývá | Kde běží |
|---|---|---|---|
| Unit | `pytest`, bez DB nebo s DB (`pytest-django`, `@pytest.mark.django_db`) | služby (cena, sedadla, kapacita, generování letů, parsování legacy formátů), formuláře a validace, role | `make test` (lokálně, v kontejneru `web`) |
| View / integrační | Django `Client` | každá obrazovka: GET, POST s platnými a neplatnými daty, oprávnění rolí (403), hlášky, stránkování | `make test` |
| E2E | Playwright (Python, Chromium) | tok Sales dle spec kap. 7; přihlášení každé role a domovská stránka; tiskové stránky se otevřou | `make e2e` proti běžícímu `docker compose` stacku se seedem |
| Statická kontrola | `ruff check`, `ruff format --check`, `manage.py check`, `manage.py makemigrations --check --dry-run` | styl, chybějící migrace | `make lint` |

`make check` = `lint` + `test`. Každý PR musí projít `make check` lokálně (autor uvede výstup v popisu PR). CI se nepoužívá (rozhodnutí projektu).

### 8.2 Docker Compose

```yaml
services:
  db:
    image: postgres:16
    environment: POSTGRES_DB=airlines, POSTGRES_USER=airlines, POSTGRES_PASSWORD=airlines
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: pg_isready
  web:
    build: .
    command: python manage.py runserver 0.0.0.0:8000
    volumes: [.:/app]
    ports: ["8000:8000"]
    environment: DJANGO_SETTINGS_MODULE=config.settings.dev, DATABASE_URL=postgres://airlines:airlines@db:5432/airlines, LEGACY_ROOT=/legacy
    depends_on: db (healthy)
  e2e:
    profiles: [e2e]
    image: mcr.microsoft.com/playwright/python:v1.4x-jammy
    volumes: [.:/app]
    environment: BASE_URL=http://web:8000
    command: pytest tests/e2e
```

Kořen repozitáře se do `web` mountuje jako `/legacy` (read-only), aby `seed_demo` četl JSON/XML z legacy adresářů. Testy používají samostatnou DB `airlines_test` (pytest-django ji vytváří automaticky).

### 8.3 Makefile (cílové příkazy)

| Cíl | Příkaz |
|---|---|
| `make up` | `docker compose up -d db web` |
| `make down` | `docker compose down` |
| `make migrate` | `docker compose exec web python manage.py migrate` |
| `make seed` | `docker compose exec web python manage.py seed_demo` |
| `make test` | `docker compose exec web pytest -q tests/unit tests/views` |
| `make e2e` | `docker compose --profile e2e run --rm e2e` |
| `make lint` | `docker compose exec web sh -c "ruff check . && ruff format --check . && python manage.py check && python manage.py makemigrations --check --dry-run"` |
| `make check` | `lint` + `test` |
| `make shell` | `docker compose exec web python manage.py shell` |

Vše musí být spustitelné i bez Dockeru (`pip install -e .[dev]`, lokální PostgreSQL, `DATABASE_URL`), ale Docker je referenční cesta.

## 9. Bezpečnost a provoz (minimum)

- `SECRET_KEY`, `DATABASE_URL`, `ALLOWED_HOSTS` z prostředí (`.env.example` v repu, `.env` v `.gitignore`).
- `manage.py check --deploy` bez varování v `config.settings.prod` (krok R18).
- Logování: prodeje (`sales.services`) a přihlášení na INFO; SQL chyby na ERROR.
- Žádné externí CDN – všechny statické soubory vendorované (offline běh).
- Aplikace se nasazuje jako jeden kontejner (`gunicorn`) + PostgreSQL; nasazení není součástí PoC.

## 10. Co se záměrně nedělá

- Žádné REST API (přidá se až s reálnou potřebou; modely jsou na to připravené).
- Žádná JS build pipeline, žádný SPA framework.
- Žádné asynchronní úlohy (tisky jsou synchronní HTML stránky).
- Žádný multitenant, i18n, audit trail nad rámec logu.
